# M8R-08A MCP Host Compatibility Matrix

## Scope and interpretation

This matrix is a dated interoperability preflight, not a promise that every vendor surface implements the same MCP revision. Evidence was retrieved on **2026-08-12**. `HOST_DOC` means first-party product documentation; `HOST_SOURCE` means first-party host source; `OFFICIAL_ISSUE_OR_DISCUSSION` is supporting evidence, not a product contract. `INFERENCE` is stated explicitly.

Three controls must not be conflated:

1. **Host tool approval** decides whether a host invokes a tool. It may be remembered or bypassed.
2. **MCP elicitation** is a protocol interaction in which a server requests structured input and receives `accept`, `decline`, or `cancel` through a capability-advertising client.
3. **Local Service confirmation fields** are application inputs. A model can author them, so `confirm=true` alone is not human proof.

The recommended M8R-08B v1 exposes only autonomous-safe tools and therefore does not depend on elicitation or host approval for its security boundary.

## Host details

### Codex

- **Transport:** `HOST_DOC`, HIGH. The Codex app, CLI, and IDE extension support command-launched stdio and URL-based Streamable HTTP. A localhost HTTP URL is documented as valid. Configuration supports environment allowlists, bearer/OAuth headers, timeouts, enabled-tool allowlists, and per-tool approval modes. [Codex MCP documentation](https://developers.openai.com/codex/mcp/)
- **Elicitation:** `HOST_SOURCE`, HIGH. Current Codex source contains form, URL, and OpenAI extended-form handlers and `accept`/`decline`/`cancel` outcomes. It is `SUPPORTED_WITH_LIMITATIONS`: interactive frontends may render forms, while delegated/noninteractive modes can cancel or fail; required-field behavior under auto-approval has had defects. [Codex elicitation source](https://github.com/openai/codex/blob/main/codex-rs/codex-mcp/src/elicitation.rs), [app-server elicitation event](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md), [required-field auto-approval issue](https://github.com/openai/codex/issues/23383)
- **Tools and annotations:** `HOST_DOC`/`HOST_SOURCE`, HIGH. Codex consumes `readOnlyHint` for its `writes` approval mode and has conservative policy behavior for unannotated tools. Annotations affect UX/policy selection but are not server-side authorization. [Codex MCP documentation](https://developers.openai.com/codex/mcp/), [tool-call policy source](https://github.com/openai/codex/blob/main/codex-rs/core/src/mcp_tool_call.rs)
- **Other primitives:** `HOST_SOURCE`, HIGH for resources; sampling is not implemented in inspected source and remains a feature request. Prompts were not found in the inspected current client (`INFERENCE`, MEDIUM). [Codex MCP client](https://github.com/openai/codex/blob/main/codex-rs/rmcp-client/src/rmcp_client.rs), [sampling request](https://github.com/openai/codex/issues/4929)
- **Approval UX:** host tool approval happens before a call and can be configured `auto`, `prompt`, `writes`, or `approve`, including per-tool overrides. It is not visible to the Local Service as a human attestation and does not answer elicitation.
- **Local/auth/version constraints:** `HOST_DOC`, HIGH. Local stdio and loopback Streamable HTTP are configurable; bearer tokens and OAuth are documented. Exact negotiated MCP revision can vary by released surface (`INFERENCE`, MEDIUM), so acceptance must record the installed host version and negotiated behavior. [Codex MCP authentication/configuration](https://developers.openai.com/codex/mcp/)
- **M8R implication:** stdio is directly compatible with the recommended v1. Action tools remain deferred even though some Codex modes support elicitation, because host mode is variable and ordinary approval may be automatic.

### ChatGPT and OpenAI hosted MCP surfaces

- **ChatGPT custom apps transport:** `HOST_DOC`, HIGH. ChatGPT web connects to public HTTPS Streamable HTTP. It does not directly attach to a loopback-only server or local stdio process. The official Secure MCP Tunnel can bridge private HTTP or stdio during development. [Connect an MCP server to ChatGPT](https://developers.openai.com/plugins/deploy/connect-chatgpt), [developer mode](https://help.openai.com/en/articles/12584461-developer-mode-and-full-mcp-connectors-in-chatgpt-beta)
- **Elicitation:** `HOST_DOC`, MEDIUM. Current server guidance tells builders to use MCP elicitation for missing structured input, but inspected ChatGPT host documentation does not state whether form mode, URL mode, or both are supported. Classification under the required vocabulary: `SUPPORTED_WITH_LIMITATIONS`; the specific limitation is that exact modes are unknown. [Build an MCP server](https://developers.openai.com/plugins/build/mcp-server)
- **Approval UX:** `HOST_DOC`, HIGH. Depending on permissions, action context and risk, ChatGPT may require confirmation for write/modify actions, and especially risky actions may be blocked. This is host-side invocation approval, not proof that a particular MCP elicitation schema was answered. [Developer mode and MCP apps](https://help.openai.com/en/articles/12584461-developer-mode-and-full-mcp-connectors-in-chatgpt-beta)
- **Hosted Responses API:** `HOST_DOC`, HIGH. Remote MCP supports remote Streamable HTTP or HTTP/SSE plus application-mediated `require_approval` and `mcp_approval_response`, including a `never` policy; no elicitation callback is documented. Tool-call approval is not elicitation. Classification for elicitation on this surface: `NOT_DOCUMENTED`. [MCP and Connectors](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)
- **Primitives/auth/version constraints:** `HOST_DOC`, HIGH for tools and server instructions; generic resource browsing, prompts and sampling are `NOT_DOCUMENTED`. OAuth is supported for deployed connectors. Full write-capable custom MCP remains plan/surface dependent, so M8R acceptance must identify the exact ChatGPT surface. [Build an MCP server](https://developers.openai.com/plugins/build/mcp-server), [developer mode availability](https://help.openai.com/en/articles/12584461-developer-mode-and-full-mcp-connectors-in-chatgpt-beta)
- **M8R implication:** a local-first stdio server is not directly usable by ChatGPT web. Secure MCP Tunnel is a later operator/development compatibility path, not part of M8R-08B and not a reason to expose a network listener.

### Claude Desktop

- **Transport:** `HOST_DOC`, HIGH. Local `claude_desktop_config.json`/MCPB extensions run a local process; remote custom connectors use Streamable HTTP (with legacy SSE retained) from Anthropic cloud. Cloud connectors cannot reach localhost, VPN-only or private-network endpoints. No first-party contract was found for directly registering a loopback Streamable HTTP URL as a local Desktop connector. [Local MCP servers](https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop), [connector building](https://claude.com/docs/connectors/building), [remote network behavior](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- **Elicitation:** `NOT_DOCUMENTED`, MEDIUM. No first-party Claude Desktop document inspected here makes an explicit form/URL elicitation capability promise; Anthropic's pinned developer guidance explicitly says Desktop is unconfirmed. Claude Code support must not be projected onto Desktop. [Pinned developer guidance](https://github.com/anthropics/claude-plugins-official/blob/c54b5608d9be1910de9a5b91c2d15bf6673b9c35/plugins/mcp-server-dev/skills/build-mcp-server/SKILL.md#L75-L80)
- **Approval UX:** `HOST_DOC`, HIGH. Desktop offers an **Allow always** tool choice and lets users disable tools through Search and tools; Research can invoke already-enabled connector tools without another approval prompt. Persistence details are not a server-visible human attestation, and none of this is elicitation. [Remote connector behavior](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- **Primitives/local/auth constraints:** `HOST_DOC`, HIGH. Remote connectors support tools, resources and prompts; sampling and resource subscriptions are not supported. Remote connection originates in Anthropic cloud and cannot reach localhost/private networks. For Local-First use, a local Desktop extension/stdio process is the supported shape; sensitive extension settings use OS-secure storage. [Connector protocol features](https://claude.com/docs/connectors/building), [remote network behavior](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp), [local Desktop MCP](https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop)
- **M8R implication:** stdio/local-extension acceptance must be manually verified on the target Desktop release. No action tool may rely on Desktop elicitation until the client advertises the exact mode at runtime and an operator UI test passes.

### Claude Code

- **Transport:** `HOST_DOC`, HIGH. Claude Code supports `stdio`, Streamable HTTP (`http`), retained `sse`, and remote WebSocket via `type:"ws"` in JSON; WebSocket is header-auth only, has no OAuth, and is not accepted by `claude mcp add --transport`. [Claude Code MCP documentation](https://code.claude.com/docs/en/mcp)
- **Elicitation:** `HOST_DOC`/`HOST_SOURCE`, HIGH. Claude Code 2.1.76 introduced full structured form and browser-URL elicitation plus hooks. Interactive mode renders the UX; noninteractive use depends on an `Elicitation` hook or SDK callback and must not be assumed to present a human UI. Classification: `SUPPORTED_WITH_LIMITATIONS`. [Claude Code MCP documentation](https://code.claude.com/docs/en/mcp), [Claude Code changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- **Approval UX:** `HOST_DOC`, MEDIUM. Claude Code permissions can approve, deny, or bypass tools. That host policy must not be treated as Local Service human proof; noninteractive modes are especially unsuitable for authorization.
- **Primitives/local/auth constraints:** `HOST_DOC`, HIGH. Tools, resources and prompts are supported; resources use `@server:URI` plus list/read helpers and prompts become `/mcp__server__prompt`; Anthropic's connector feature page says sampling is not. Direct stdio and loopback HTTP are usable. HTTP supports browser OAuth/refresh and headless paste-back paths, while static headers are configurable. Current npm version observed was 2.1.228. [Claude Code MCP documentation](https://code.claude.com/docs/en/mcp), [connector feature support](https://claude.com/docs/connectors/building)
- **M8R implication:** recommended safe stdio tools are compatible. A future action-tool experiment would have to require advertised elicitation, interactive mode, explicit accept, and all Local Service identity bindings—never just Claude Code tool permission.

### VS Code Copilot Chat

- **Transport and primitives:** `HOST_DOC`, HIGH. VS Code supports local stdio, Streamable HTTP, retained SSE, tools, prompts, resources/templates, sampling, roots, OAuth, instructions, and MCP Apps. [MCP extension guide](https://code.visualstudio.com/api/extension-guides/ai/mcp), [MCP configuration](https://code.visualstudio.com/docs/agents/reference/mcp-configuration)
- **Elicitation:** `HOST_DOC`, HIGH. Current VS Code documentation supports form elicitation, and VS Code 1.107 explicitly added MCP 2025-11-25 URL-mode behavior. Classification: `SUPPORTED` (`SUPPORTED_FORM_AND_URL` descriptively). [MCP extension guide](https://code.visualstudio.com/api/extension-guides/ai/mcp), [VS Code 1.107 release notes](https://code.visualstudio.com/updates/v1_107)
- **Annotations:** `HOST_DOC`, HIGH. `readOnlyHint` can affect pre-execution confirmation; `openWorldHint` can trigger review of external output. No equally precise current commitment was found for every annotation (`INFERENCE`, MEDIUM). [MCP extension guide](https://code.visualstudio.com/api/extension-guides/ai/mcp), [VS Code 1.106 release notes](https://code.visualstudio.com/updates/v1_106)
- **Approval UX and bypass:** `HOST_DOC`, HIGH. Approval can be scoped once/session/future; Bypass Approvals and Autopilot auto-approve tool calls. Sandboxed stdio MCP servers can be auto-approved on macOS/Linux, not Windows. [Approvals and permissions](https://code.visualstudio.com/docs/agents/approvals), [MCP servers](https://code.visualstudio.com/docs/agent-customization/mcp-servers)
- **Local/auth/version constraints:** `HOST_DOC`, HIGH. Loopback and remote servers are configurable; OAuth, roots and server instructions are documented. Background agents have narrower interactive/auth constraints, so acceptance must use the intended Copilot surface rather than infer from desktop Chat. [MCP extension guide](https://code.visualstudio.com/api/extension-guides/ai/mcp), [MCP configuration](https://code.visualstudio.com/docs/agents/reference/mcp-configuration)

### Gemini CLI

- **Transport:** `HOST_DOC`, HIGH. Gemini CLI supports stdio, Streamable HTTP configured with `httpUrl`, and legacy SSE configured with `url`; local stdio is the default. [Gemini CLI MCP servers](https://geminicli.com/docs/tools/mcp-server/)
- **Elicitation:** `HOST_SOURCE`, HIGH. Current MCP client advertises roots but no elicitation capability and registers no elicitation handler. Classification: `NOT_SUPPORTED`. [Gemini MCP client source](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/tools/mcp-client.ts)
- **Tools/resources/prompts:** `HOST_DOC`/`HOST_SOURCE`, HIGH. All three are discovered; sampling is absent from the inspected client (`HOST_SOURCE`, HIGH).
- **Annotations:** `HOST_SOURCE`, HIGH. Current source consumes `readOnlyHint`; no inspected path establishes equivalent behavior for `destructiveHint` or `openWorldHint`. [MCP client source](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/tools/mcp-client.ts), [MCP tool source](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/tools/mcp-tool.ts)
- **Approval UX and bypass:** `HOST_DOC`, HIGH. In a trusted current folder, `trust:true` / `--trust` can bypass MCP confirmations; policies can allow calls, and `--yolo` auto-approves all calls. Noninteractive `ask_user` becomes deny. [MCP server guide](https://geminicli.com/docs/tools/mcp-server/), [policy engine](https://geminicli.com/docs/reference/policy-engine/)
- **Local/auth/version constraints:** `HOST_DOC`, HIGH. Local stdio/HTTP work in a trusted folder; remote HTTP/SSE supports browser OAuth, which has headless constraints. No current host guide fixes one negotiated MCP revision, so acceptance must record the installed version (`INFERENCE`, MEDIUM). [Gemini CLI MCP servers](https://geminicli.com/docs/tools/mcp-server/)
- **M8R implication:** Strategy B cannot be the portable v1 because Gemini cannot answer elicitation. Strategy A works, including in trusted/yolo mode, because its exposed operations cannot authorize or execute.

### Hermes Agent

- **Transport:** `HOST_DOC`/`HOST_SOURCE`, HIGH. Main snapshot `a871948…`, whose `pyproject.toml` declares 0.20.0, supports local stdio, Streamable HTTP, and explicitly configured legacy SSE. This is a pinned source snapshot, not a claim that a published 0.20.0 artifact was independently verified. [Pinned Hermes MCP guide](https://github.com/NousResearch/hermes-agent/blob/a871948d8d4b0f774d4ec40467bab1078a9f28d5/website/docs/user-guide/features/mcp.md), [package constraints](https://github.com/NousResearch/hermes-agent/blob/a871948d8d4b0f774d4ec40467bab1078a9f28d5/pyproject.toml)
- **Elicitation:** `HOST_SOURCE`, HIGH for implementation and MEDIUM for frontend UX. Form mode is presented as a consent request, but acceptance returns `content:{}` rather than collecting structured values; URL mode always declines. Timeout and handler errors fail closed. With `trust:untrusted`, tools lacking exact `readOnlyHint:true` require per-call consent with no remembered-allow path; read-only-hinted tools skip it. [Pinned MCP guide](https://github.com/NousResearch/hermes-agent/blob/a871948d8d4b0f774d4ec40467bab1078a9f28d5/website/docs/user-guide/features/mcp.md), [package constraints](https://github.com/NousResearch/hermes-agent/blob/a871948d8d4b0f774d4ec40467bab1078a9f28d5/pyproject.toml)

## Approval portability conclusion

Host tool confirmation is neither universal nor durable: Codex, VS Code, Gemini, Claude Code, and Hermes all have modes or policies that may pre-approve tools; ChatGPT has its own confirmation model; Inspector is a test tool. Elicitation is materially stronger than a model-supplied argument because a capable client handles a distinct protocol request and returns an explicit action, but it proves only that the client returned that action. It does not cryptographically prove human identity, prevent a client from automating acceptance, or replace Preview/Plan/Authorization/scope/claim binding.

Therefore:

- MCP v1 uses **Strategy A: safe tools only**.
- `market_authorize_request` and `market_execute_request` are absent, not merely described as dangerous.
- Unsupported elicitation is irrelevant to v1 safe tools and must fail closed if action tools are ever introduced.
- A future action-tool proposal must re-run this matrix against actual released host versions and must never fall back to model-authored confirmation fields.

## Known unknowns

- ChatGPT's exact advertised form/URL elicitation modes are not stated in the public host documentation inspected.
- Claude Desktop elicitation support and persistent approval semantics are not documented precisely enough to claim support.
- Codex, Claude Code, and Hermes behavior varies across interactive, delegated, SDK, print, messaging, or auto-approval surfaces.
- Inspector protocol-era behavior differs: pin the release and test legacy elicitation and modern MRTR separately in the Web client; its CLI is not an elicitation acceptance surface.
- Generic clients may ignore annotations, omit elicitation, retry tool calls, or be malicious. Local Service validation and single-use governance remain authoritative.
